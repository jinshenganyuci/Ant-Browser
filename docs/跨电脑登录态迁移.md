# 跨电脑迁移登录态

## 为什么旧包可能导入后退出登录

旧版实例包原样复制 Chromium 用户目录，包括 Cookie 数据库与 `Local State`，但没有独立导出浏览器可读取的 Cookie。Windows 的加密数据通常绑定来源系统用户/电脑；新版本 Chrome 还可能使用应用绑定加密。复制数据库和原来的密钥文件，不等于目标电脑可以解密这些 Cookie。

本修复不破解、绕过系统加密保护，也不关闭 Chrome 的加密机制。它使用用户所选实例提供的本机 CDP 浏览器接口，在来源端读取 Cookie，在目标端交由目标浏览器写入并管理。

## 正确使用方式

1. **来源电脑与目标电脑都更新到支持跨电脑登录态迁移的修复版。**
2. 在来源电脑启动要迁移的实例，确认目标网站仍处于登录状态，**保持实例运行，然后点击导出**。
3. 确认导出提示。程序会读取 Cookie、正常关闭所选实例以完成用户目录写入，再生成 ZIP。关闭浏览器不是点击网站“退出登录”。
4. 把 ZIP 传到自己的目标电脑并导入。启动导入的实例时，程序先恢复和读取校验 Cookie，再打开配置的启动页。
5. 程序在关闭来源实例之前先保存一份私有、一次性的恢复快照：即使后续打包失败也能重试，来源实例下次启动也能恢复导出时的会话 Cookie。
6. 来源端或目标端恢复成功后，各自的一次性登录态文件会删除。之后正常使用不会反复注入旧 Cookie，也不会把主动退出的账号重新登录。

含 Cookie 数据库但已停止的实例不能被当作“可迁移登录态”直接导出：程序会要求在来源电脑启动实例后再导出，避免把仅有原电脑密文的 ZIP 误报成迁移成功。尚未使用的新实例、以及已经导入但尚未启动的可迁移实例，可以直接导出。

## 第一次启动的差别

迁移第一次启动暂时关闭扩展，不恢复旧标签页，也不使用可能立即打开网站的自定义启动参数；指纹和代理的受支持设置保留。Cookie 恢复并校验成功后才打开启动页，下次启动恢复正常行为。

如果浏览器拒绝 Cookie、调试接口未就绪或读取校验不完整，程序会停止本次启动并保留待恢复数据，不会悄悄略过失败项后宣布成功。

## 安全与能力边界

- **ZIP 包含可直接登录网站的 Cookie，应按密码文件保管，不要上传公开仓库、公开网盘或发送给他人。**当前 ZIP 不进行密码加密；应使用私密传输渠道。
- 旧 ZIP 没有独立 Cookie 数据时，目标电脑无法凭空补回来源端解密后的 Cookie，需要回来源电脑用新版重新导出。如果来源电脑也已经退出网站，需要先在来源端正常重新登录。
- 本修复覆盖浏览器允许通过 CDP 获取和恢复的 Cookie，保留会话/持久类型、域名与路径作用域、HttpOnly、Secure、SameSite、有效期和可序列化的 CHIPS 分区信息。
- 不把会话 Cookie 强制改成长期 Cookie。网站设置了会话生命周期时，之后关闭浏览器是否需重新登录仍由原有会话策略决定。
- 不透明分区等无法完整迁移的数据会明确报错，而不是忽略。过期 Cookie 不复活。
- 保存的密码、系统证书、Passkey、设备绑定密钥不属于此 Cookie 修复的迁移范围。已有 Local Storage / IndexedDB 等目录仍按实例包原有方式复制。
- 站点可能根据 IP、设备特征、会话过期或异地风控要求重新验证；不能承诺所有网站永远免登录，也不能保证网站服务器不会调整其他设备的会话。
- 自动备份仍属于原始数据备份，不等同于从运行中实例生成的跨电脑登录态导出。

## 云端验证

工作流 `.github/workflows/portable-session-test.yml` 在 GitHub Actions 执行，不需要在本地构建或测试。真实 Chrome 用例使用全新的临时用户目录和虚构 `.test` 域 Cookie，不读取个人浏览器数据，不登录任何第三方账号。

验证内容包括：旧导入遗漏登录态的回归、ZIP 往返、目标端新 `Local State`、首次业务导航前恢复、host-only/HttpOnly/Secure/SameSite/CHIPS、会话 Cookie、目标重启后的持久 Cookie，以及失败保留、一次性消费和运行时文件隔离。通过与否以对应提交的 Actions 结果为准，不以文档文字代替执行结果。
